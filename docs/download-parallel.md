# ダウンロードの並列処理

「マイダウンロード」の「ダウンロードの変換並列数の上限」で変更する。初期値は3。設定はブラウザのlocalStorageに保存し、このタブで実行するダウンロードに適用する。常時3並列にする設定ではなく、復号・BGZF解凍のCPU処理の上限である。通信はタブ全体で1リクエストに固定する。CPU処理はブラウザのhardwareConcurrencyも上限に使い、不明な場合は1とする。上限の引き下げは実行中ジョブの完了後、新規投入に反映する。

## 処理と互換性

- 通常のWorker管理ダウンロード、アーカイブ復号、アーカイブからZIPへの変換に適用する。ブラウザに直接渡すリンク、HLS変換、ディレクトリ内ファイルの取得順序は変更しない。
- HTTP Rangeは32MiBで、先頭から直列に取得する。最初の応答で全長とstrong ETag / Last-Modifiedを固定してから先読みする。206、Content-Rangeの開始・終端・全長、本文長、validatorの一致を確認する。空のオブジェクトは `416 Content-Range: bytes */0` を受け付ける。
- 復号はIVを除いた暗号文本体の位置を使用する。1MiBの16バイト境界に揃えたジョブと最後の端数に分割する。`decryptAesCtrRange` 自体は任意位置を受け付け、非整列位置ではCTRのキーストリーム先頭を読み飛ばす。
- BGZFのブロック解析と解凍を共通化した。残り全体を繰り返しコピーせず、ブロック途中の端数だけを64KiBの作業領域へコピーする。CPUジョブは圧縮入力・解凍出力それぞれ最大1MiBの完全なブロック群。gzipデコーダーによるCRC/ISIZE検証に加え、出力の上限を確認する。
- 復号とBGZF解凍のジョブは、両方の管理Workerで共有する処理Workerプールへ転送する。専有ArrayBufferをtransferし、結果を順序どおりに流す。単一ファイル内も並列に復号する。
- tar解析、各エントリーの順序、通常gzipの解凍、標準gzipへの再圧縮を維持する。出力gzipをBGZFや複数gzipの連結に変更しない。直接保存、アプリのService Worker保存、OPFSの既存経路を利用する。

## メモリと失敗処理

メモリの予約上限は通信64MiB＋処理64MiB。各ダウンロードは開始前に通信32MiBと処理32MiBを予約し、予約できるまで待機する。この保守的な予約により同時に進行する対象ダウンロードは最大2件となる。CPUプールと直列通信枠はタブ全体で共有し、予約済みダウンロード間で割り当てる。CPUは設定値が大きくても実装のメモリ上限として8までに制限する。

受信本文はチャンクごとにOPFSの範囲別ファイルへ書き込む。完成した範囲から1MiBずつ読み、復号・解凍へ渡す。受信中と消費中を含め最大4範囲（128MiB/ダウンロード、入場上限2件で256MiB）を保持し、読み終えたファイルは削除する。取得完了を全ファイル分待たずに変換を進める。OPFS非対応・利用拒否時は32MiBの取得単位を維持し、RAMに1範囲だけを保持する。空き容量不足や書き込み失敗時は、そのダウンロードをエラー終了し、GETを繰り返さない。

CPU各段階の先読み・順序待ちを4ジョブ以内に固定する。通信予約は受信とRAMフォールバックを含む。処理予約は最大2段階の入力/出力、作成中ジョブ、BGZFの端数、tar/保存への引き渡しを含む。先に下流の領域を予約するため、全容量を通信が占有してCPU処理が進まない状態を避ける。プールにも1MiBバッファと最大8未完了ジョブ/ダウンロードの検査を設ける。

保存が止まると新たなpullが止まり、上記ウィンドウを超えた取得・処理は行わない。失敗・取消時はそのダウンロードのAbortSignal、待機ジョブ、実行中の処理Worker、ポート、予約を解放し、他のダウンロードを継続する。一時ファイルの削除を待ってから予約を返す。画面遷移では終了させない。OPFSの専用ディレクトリとWeb Locksで所有権を管理し、強制終了で残ったファイルは次回起動時に、他タブを含め所有者のロックがない場合のみ削除する。

128MiBはアプリ管理パイプラインの保守的な予約値であり、ブラウザのネットワーク、転送ストリーム、圧縮エンジン、Workerランタイム、OSファイルキャッシュを含むプロセス全体のメモリ上限ではない。

## 自動調整と計測

CPUは1から開始し、通信は常に1のままにする。通信の本文read待ち時間（OPFS書き込み時間を除く）とCPU Worker内の実処理時間を分離して計測し、通信入力と比較可能な最初のCPU段階から必要なCPU数を推定する。後段の復号出力を通信量と直接比較しない。

CPU段階ごとの2秒以上かつ3サンプル以上の観測窓で、未処理ジョブがあればCPUの並列数を1増やす。入力の実効スループットが10%以上改善しなければ戻し、試行後5秒は次の増加を行わない。保存のバックプレッシャーは段階ごとのウィンドウで伝播する。短時間で完了する処理では試行窓に到達せず、初期推定のまま終了する。

内部診断 `getDownloadDiagnostics()` は現在/最大の予約量、CPU・通信の目標/実行数、受信量、累積処理時間を返す。設定用UIに内部診断は表示しない。CPU時間・受信時間は並列ジョブの累積値なので、壁時計の総時間と単純に足し合わせない。

## 検証方法

```sh
pnpm --filter app exec vitest run test/download-parallel.test.ts test/download-resilience.test.ts test/encryption.test.ts test/decrypted-tar.test.ts
pnpm --filter bgzf test
pnpm --filter app exec playwright test --config playwright.download.config.ts
DOWNLOAD_BENCHMARK=1 pnpm --filter app exec playwright test --config playwright.download.config.ts test/e2e/download-benchmark.spec.ts --reporter=line
```

Ubuntu 26.04ではPlaywright 1.60.0のFirefox配布先判定が未対応だったため、インストール済みの対応リビジョン1522を `PLAYWRIGHT_HOST_PLATFORM_OVERRIDE=ubuntu24.04-x64` で実行した。

ブラウザテストは実Workerの共有上限3、設定保存、上限引き下げ、内容一致、保存失敗の独立性、SW保存、OPFS/指定ファイルハンドル、gzip/ZIP変換を確認する。指定ファイルハンドルのテストはOPFSから作成した実ハンドルで直接書き込み分岐を確認し、OSの保存ダイアログ操作は行わない。FirefoxのSW応答エラーではPlaywrightの `download.failure()` が完了しない既知の制約があるため、その終了通知を検査する2件だけを明示的にskipする。Firefoxでもパイプラインの保存失敗・予約解放は別のテストで確認する。

## 性能比較と検証記録

同一の32MiB＋19バイトの疑似乱数データから、暗号化ファイル、BGZF、暗号化エントリーを含むtar.gzを作成する。比較対象は `001d6dd` の変換、同変換のBGZF反復コピーのみを除去したもの、32MiB直列取得・OPFS・共有CPUプール版。測定用HTTPサーバーはlocalhostで、slow-networkは各接続を64KiB/8ms、slow-saveは出力を約8MiB/sに制限する。各ケース1回の測定であり、本番や実インターネット回線の速度を保証する数値ではない。ハッシュ検査用の出力保持領域は測定ハーネスのもので、パイプライン予算の外にある。

[以前の4MiB並列取得版の計測](benchmarks/download-parallel-2026-09-13.json) は設計変更前の履歴であり、現在の32MiB直列OPFS版の性能ではない。特に以前の低速回線で通信が2並列に増えた結果は、現在の動作には当てはまらない。

新しい機能テストでは160MiB＋19バイトを32MiBずつ計6 GETで取得し、OPFSに4範囲で先読みが止まること、読み取り後の削除と内容を検査する。4MiBの場合は同じ入力に41 GETが必要になる。取消とOPFS非対応時の32MiB維持、容量不足時の再試行禁止、タブ内の通信共有上限1も検査する。
